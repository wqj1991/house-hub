# ADR 0002 — 本地优先：Tauri + 一台 SQLite，没有服务端

> 迁入自 `D:\repos\house\docs\adr\0002-本地优先.md`（2026-11-13）。本仓库为真值；house 仓库的同名副本待其退役时删除。

**背景**：这套东西要在手机上看（Android 必须支持），而上一代 `luohu` 是 fastify + 浏览器的一个 localhost 服务。手机上没有 node，也没有「本地起服务再连 127.0.0.1」这条路的稳定实现；就算用 Termux 塞一个 node 进去，也会把「打开就能看」变成「先起服务」。数据量是几千个小区、几万条成交、几百条路线——单文件 SQLite 完全是舒适区。

**决定**：应用形态 = Tauri 2 单进程。前端 React 19 + TS + Vite 7 + shadcn/ui；后端是 Rust，只负责三件事：打开 `app_data_dir/house.db`、执行 `schema.sql`、暴露 `search_communities / get_community / shortlist_*` 这几个命令。抓数、路径规划这些重活不进 app——它们是独立的本地脚本，跑完把行灌进同一个库。

**为什么不是别的**：
- **把 fastify 塞进 Tauri sidecar**：多一个二进制、多一个端口、多一套崩溃面，换来的是「可以用 node 写业务」。可这里的业务是 SQL 与打分函数，Rust 写不比 node 难。
- **纯 Web + IndexedDB**：手机上能用，但数据会跟着浏览器 profile 走，换个壳就丢；而且没法跑抓取脚本直接落库。
- **远端 API**：这台机器是私人工具，没有运维预算；一旦要「随时能看」，就得有人保证服务活着。

**后果**：
- 抓数与路径规划是**离线批处理**，不是 app 内实时请求。所以界面上的数字永远是「某天抓的」，`fetched_at` 必须显示出来——这不是缺点，是诚实。
- 打分/积分是 SQL + Rust 里的纯函数，改规则要发版；反过来，规则表 `score_rule` 留在库里，权重可以不改代码就调。
- 迁移成本：`luohu` 的 6.2 万条成交得先导出成 SQL/JSON 再灌进来。这一步一次性，且必须做（见 DESIGN §7 第 1 条）。
