# ADR 0005 — 多端一后端：本地优先保留，加一台同步中枢

背景：ADR-0002 写的是「Tauri 单进程，没有服务端」，理由是手机上没有 node、私人工具没有运维预算。v0.1 落地后事实变了三件：

1. 要出 Web 端（大屏对比、发给家人看、不装客户端），而 Web 拿不到 Tauri IPC，src/db.ts 的 19 个命令全部失效。
2. 小区与成交数据要一次抓、三端共用。抓取必须固定在 VPS 出口（ADR-0004），客户端各抓一份既不稳定也不一致。
3. 两个人、多台设备，待选/清单/房源卡会同时在两处改。各存各的等于把同一份判断分裂成两份。

决定：

- 保留本地优先：桌面与移动继续用本地 SQLite，断网时都能读、能写、能算分（这正是 ADR-0002 里最值钱的那半句）。
- 增加一台服务器作为唯一真源与同步中枢：services/api（Node 22 + Hono + better-sqlite3）是 house.db 的唯一写者，提供 /sync/pull、/sync/push、只读查询与任务提交。
- 增加 Web 端：同一个 apps/web 构建产物，RemoteRepo 直连 API；离线时读快照、写 outbox。
- 抓数与重计算从「app 内的离线脚本」升级为 worker + job 队列，仍只在服务器跑，仍不带分数（ADR-0004 原则原样保留）。

为什么不选别的：

- Web 端自己连抓取源：出口 IP 一变就废；规则一改要发两次版（前端 + 爬虫）。ADR-0004 已否过一次。
- 纯云（三端都不存本地）：手机在看房现场是地下室、电梯、老小区，写操作失败等于功能不存在；3000 小区的本地搜索比网络往返快一个量级。
- 上 Postgres + 容器编排：单人家庭、万级行、单机 2C2G。多一个数据库就多一套备份/升级/连接池的维护面，换不来任何东西。
- 通用 CRDT / 自研同步引擎：冲突只有「人改的」vs「服务器抓的」两类，按表写死字段所有权 + LWW 就够；CRDT 会让「这个价格到底是谁写的」变得不可解释，而本项目第一原则是每个数都要能追溯到来源。

代价（认下来）：

- 多一个要维护的服务：systemd 两个单元、一个 openresty 前缀、一个 token、一套备份。SSH 22 外网被封，部署只能走 1Panel HTTP API，已成事实约束，写进 infra/deploy.sh。
- 同步协议是自定义的：约 300 行（outbox + pull/push + 字段所有权表），要自己写测试。不引成熟方案是因为数据模型简单到不值得。
- 客户端版本会漂移：老 APK 可能用旧规则算分。用 /rules 的 hash 校验 + 页面黄条公示，不静默。
- Web 断网只读（能读上次快照，不能本地全文搜索新数据），与桌面/移动能力不对等。这个不对等是刻意的。

边界（什么情况下重新考虑）：

| 触发 | 重新考虑什么 |
|---|---|
| 并发写 > 10/s，或出现第二个家庭 | SQLite 迁 Postgres；device 变成 user + household |
| 数据量 > 50 万行 / 查询 > 200 ms | 加索引或迁 Postgres，二选一 |
| 需要实时协作（两人同时改同一套房源卡） | 才考虑 SSE + 行锁提示；仍不引 CRDT |
| 服务器 SLA 变成刚需 | 加只读副本或托管数据库；先看备份演练结果 |
